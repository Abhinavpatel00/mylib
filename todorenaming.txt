Note on mu_hash32 vs mu_hash64: today "hash32" stores a uint64 key and a
uint32 value, while "hash64" stores uint64 key and uint64 value. The number
tracks the VALUE width, not the key. If you rename, either keep that meaning
(mu_hash32 = u32 values) or rename by intent (mu_hash_u32_value /
mu_hash_u64_value) so the suffix isn't misleading.

 D. DUPLICATE / COMPETING IMPLEMENTATIONS  (the real inconsistencies)
================================================================================
These are behaviour-level, not just names. Decide one winner per row.

D1. Five (5) u64 hash tables exist under three naming schemes:
    - mu_hash_table.h: `hash_t` family (hash_init/free/find_slot/put/get),
      sentinel HASH_EMPTY = 0, NO asserts, u64->u64.
    - mu_hash_table.h: `mu_hash32_static_t` (caller-owned arrays, u64 key,
      u32 value, sentinel MU_HASH_UNUSED = all-ones).
    - mu_hash_table.h: `mu_hash32_t` (heap-owned, u64 key, u32 value,
      currently only MU_ASSERTs and NO resizing).
    - mu_min_containers.h: `mu_hash64` (heap-owned, u64->u64, tombstones,
      rehash, pow2 capacity) — the most complete one.
    - mu_min_containers.h: `mu_hash64_static` (fixed, caller-owned).
    -> Recommend: keep ONE owned u64->u64 table (`mu_hash64`), one fixed
       caller-owned table, and ONE u32-value variant. Delete the `hash_t`
       family and `mu_hash32_static_t`/`mu_hash32_t` duplication.

D2. mu_hash64_mix() is DEFINED TWICE with identical bodies:
      mu/mu_hash_table.h:324  and  mu_min_containers.h:150
    Any translation unit that includes both headers gets a redefinition error
    (MU_INLINE = static inline is exempt only within one TU, but a duplicate
    definition in the SAME TU is an error; these are different functions with
    the same name -> hard error). Move the mix function to ONE place
    (suggest mu_common.h or a new mu_hash.h) and include it.
    Also MU_HASH_UNUSED is #defined twice (mu_hash_table.h and
    mu_min_containers.h) — fold into one.
    Note: today mu.h includes mu/mu_hash_table.h but NOT mu_min_containers.h,
    so the collision is currently latent — but it will bite as soon as both
    are pulled into the same TU.

D3. TWO dynamic-array implementations with different macro prefixes:
      mu/mu_array.h          : array_header_t, array_push/size/reserve/free/pop/back
      mu_min_containers.h    : mu_array_header, mu_array_push/size/reserve/free/...
    -> Pick one (recommend the mu_array_* names in mu_min_containers.h, which
       are already prefixed and match the convention) and delete the other, or
       keep one as the base and make the other a thin alias layer.
    -> ALSO: mu/mu_length_index.h calls array_reserve/array_push/array_header,
       i.e. the UNPREFIXED set, so whichever you keep, update this call site.

D4. TWO allocator headers:
      allocators.h        : mu_arena, mu_pool, mu_buddy
      mu/mu_allocators.h  : mu_buffer, mu_linear_allocator, mu_ring_allocator
    plus offset_allocator.h (OA_*) and mu_mmgr.h (debug allocator).
    -> Not necessarily wrong, but document the split clearly: put them all
       under mu/ and give each a one-line "when to use" comment, or merge the
       overlapping arena/linear concepts.

D5. TWO RNGs:
      mu/mu_pcg.h  : mu_pcg32 (in the umbrella)
      mu/mu_rand.h : rand()-based Box-Muller gaussian (NOT in the umbrella)
    -> Either make mu_rand.h build on mu_pcg32 and drop rand(), or move it out
       of mylib. Document the decision.
